What this cell does

Removes every row where CustomerID is missing, and overwrites data with that smaller, cleaner table. Then reprints .info() to confirm the fix.

Why this cell exists

Cohort analysis groups behavior by customer — the entire technique is meaningless for a transaction where you don't know who made it. Rather than guessing or filling in a fake ID, the safest move is to drop those rows entirely. This is a judgment call every analyst has to make explicitly and document, because dropping data always throws information away.

Line-by-line explanation

  • data = data.dropna(subset=['CustomerID'])
    What: scans the CustomerID column and removes any row where that cell is NaN (missing). Why subset= matters: without it, dropna() removes a row if any column has a missing value — that would also nuke every row with a blank Description, which you don't want. Restricting the check to just ['CustomerID'] is deliberate and precise. Common mistake: writing data.dropna() with no subset and silently losing far more rows than intended. What's returned: a new DataFrame (pandas doesn't modify the original in place unless you pass inplace=True) — which is why the line re-assigns it back to data. If removed: every later groupby/pivot would include phantom "no customer" rows, poisoning the cohort counts.

📦 Concept: missing values (NaN)

NaN ("Not a Number") is pandas' placeholder for "no value was recorded here." It's contagious — almost any arithmetic touching a NaN produces another NaN — which is exactly why you decide up front whether to drop those rows (dropna) or fill them with a default (fillna).
Analogy Think of a class attendance sheet with some names left blank. You can't compute "average grade per student" for a blank row — you either cross it out (drop) or write "absent" (fill) before doing any math.
Interview angle: always be ready to justify why you chose drop vs. fill — "I dropped because this field is required for the entire analysis and imputing a fake customer would bias the retention numbers" is a strong answer.

Build the Cohort Structure

This is the conceptual heart of the notebook. Cells 4–10 turn a plain transaction log into three new columns that let you ask "how many months after joining is this purchase?"

Big picture, before you dive in Every cohort analysis boils down to three ingredients per row: (1) when did this specific purchase happen? (2) when did this customer's very first purchase happen? (3) what's the gap, in whole months, between the two? Cells 4, 5, and 10 build exactly those three things, in that order.
Cell 04

Create an Invoice Month

#create an invoice month
import datetime as dt
#function for month
def get_month(x):
    return dt.datetime(x.year, x.month,1)
#apply the function
data['InvoiceMonth'] = data['InvoiceDate'].apply(get_month)
data.tail()

What this cell does

Creates a brand-new column, InvoiceMonth, that rounds every precise InvoiceDate timestamp (e.g. 2010-12-01 08:26:00) down to just the first day of that month (2010-12-01), throwing away the day-of-month and time.

Why this cell exists

Cohort analysis in this notebook works at monthly granularity — "did this customer come back in month 3?" — not at the minute or even day level. If you kept the exact timestamp, every single purchase would look "unique" and grouping customers by shared time buckets would be impossible. Rounding every date down to the 1st of its month gives you a clean, comparable label to group by.

Line-by-line explanation

  • import datetime as dt
    What: loads Python's built-in datetime module (not a third-party library — it ships with Python itself), aliased dt. Why: you need dt.datetime(...) below to construct a new date object.
  • def get_month(x):
    What: starts defining a custom, reusable function named get_month that takes one input, x. Why: pandas has no built-in "round this timestamp down to the 1st of its month" function, so the notebook author writes a tiny helper to do exactly that. What is x? When this function is applied to the column below, x will be one individual timestamp value (technically a pandas Timestamp object) at a time — never the whole column at once.
  • return dt.datetime(x.year, x.month, 1)
    What: builds a brand-new date object using only x's year and month, hard-coding the day to 1. Why: x.year and x.month are attributes already stored inside any timestamp object — no calculation needed, just extraction. What's returned: a datetime.datetime object representing the first day of that month at midnight. Common mistake: forgetting that this returns a full datetime (with a 00:00:00 time baked in) rather than a "month" data type — Python has no dedicated year-month type, so "first of the month" is the conventional stand-in.
  • data['InvoiceMonth'] = data['InvoiceDate'].apply(get_month)
    What: runs get_month once for every single row in the InvoiceDate column, and stores each result in a new column called InvoiceMonth. Why .apply(): it's the general-purpose tool for "run my own custom function against every value in this column," used whenever no built-in vectorized pandas function already does the job. Common mistake / real-world note: this notebook actually triggers a SettingWithCopyWarning here (visible in the real output below) — a signal that pandas isn't 100% sure whether data is a fresh DataFrame or a view into another one. It still works in this case, but the safe fix is data = data.copy() right after loading, or using .loc[] for the assignment. If removed: there would be no monthly bucket to group by at all — cell 5 and cell 7 both depend directly on this column existing.
  • data.tail()
    Prints the last 5 rows (as opposed to .head()'s first 5) — a good habit here specifically because it lets you confirm the new column appeared correctly at the far end of a 400K+ row table, not just near the top.

📦 Concept: what does .apply() do?

.apply() takes a function you supply and runs it once per row (or per column) of a DataFrame or Series, collecting the results into a new Series. It's the escape hatch you reach for when a built-in pandas method can't already do what you need.
Analogy Imagine handing every student in a class the same worksheet ("subtract the day, keep year+month") and collecting all 400,000 completed worksheets into one master list — that's .apply(): same instructions, applied individually to every row.
Common mistake: reaching for .apply() out of habit when a faster, vectorized pandas operation already exists (e.g. data['InvoiceDate'].dt.to_period('M') could replace this whole cell) — .apply() is convenient but noticeably slower on large datasets because it runs pure Python row-by-row instead of pandas' optimized C code.

📦 Concept: functions (def)

A function is a named, reusable block of instructions. You define it once with def name(parameters): and a return statement, then "call" it as many times as you like with different inputs, without retyping the logic.
Analogy A function is a vending machine: you put in coins (arguments), it always performs the same internal steps, and it hands back a specific product (the return value) — you never need to know how the machine works inside to use it.

Cell 05

Create a Cohort Month (first purchase)

#create a column index with the minimum invoice date aka first time customer was acquired
data['Cohort Month'] =  data.groupby('CustomerID')['InvoiceMonth'].transform('min')
data.head(30)

What this cell does

For every customer, finds the earliest InvoiceMonth they ever appear in — their acquisition month — and writes that same value onto every single row that customer has, in a new column called Cohort Month.

Why this cell exists

This is the single most important idea in the whole notebook: a cohort is "the group of customers who were all first acquired in the same month." To know if December's cohort came back in March, you first need to permanently label every one of December's transactions — and every later transaction those same customers ever make — with "December" as their home cohort.

Line-by-line explanation

  • data.groupby('CustomerID')
    What: splits the 406,829-row table into hundreds of smaller groups, one per unique CustomerID. What's returned: not a DataFrame yet — a special intermediate DataFrameGroupBy object holding "the plan" for how to split the data, waiting for you to say what to do with each group.
  • ['InvoiceMonth']
    What: tells the groupby "I only care about the InvoiceMonth column within each customer's group" — narrowing the operation before you aggregate.
  • .transform('min')
    What: for each customer's group, computes the minimum (earliest) InvoiceMonth — then, critically, broadcasts that single value back out to every row belonging to that customer, rather than collapsing the group into one row. Why transform instead of agg/aggregate: .agg('min') would return one row per customer (a much shorter table) — useless here, since you need the result to line up row-for-row with the original 406,829-row table so it can become a new column. What's returned: a Series exactly the same length as the original data. Common mistake: using .agg() when you meant .transform() and then getting a length-mismatch error when trying to assign it as a new column.
  • data.head(30)
    Prints 30 rows instead of the default 5 — deliberately more than usual here, likely so the notebook author could visually confirm that multiple different customers' Cohort Months were computed correctly, not just the first customer's.

📦 Concept: GroupBy — split, apply, combine

Every .groupby() operation follows the same three-step pattern: split the data into groups sharing a key (here, each unique customer), apply a calculation to each group independently (here, find the minimum month), then combine the results back together.
Analogy Picture sorting a pile of receipts into one folder per customer (split), writing "earliest visit: December" on a sticky note inside each folder (apply), then either keeping one sticky note per folder (.agg) or photocopying that same sticky note onto every single receipt inside the folder (.transform).

📦 Concept: transform() vs. agg() — the detail that trips everyone up

Both work on grouped data, but they return different shapes. agg('min') collapses each group to one summary row (a short table — great for reports). transform('min') keeps the original row count and repeats the group's answer on every row that belongs to it (a full-length column — required whenever you need to attach a group-level fact back onto the original data).
Analogy If a family's total grocery bill is calculated once (agg), that's one number for four people. If instead everyone in that family gets a receipt that shows "your family spent $120 total" printed on it (transform), each of the four people is holding the same number, but there are still four separate receipts.

A reusable date-element helper

# create a date element function to get a series for subtraction
def get_date_elements(df, column):
    day = df[column].dt.day
    month = df[column].dt.month
    year = df[column].dt.year
    return day, month, year

What this cell does

Defines a reusable function that, given any DataFrame and a date column's name, pulls out three separate Series: the day, the month, and the year — all at once.

Why this cell exists

You can't directly subtract one calendar date from another and get "number of months" — Python's date subtraction gives you a raw day-count (a Timedelta), not clean calendar months. The trick this notebook uses instead (in cell 10) is to subtract the year numbers and the month numbers separately, then combine them with simple arithmetic. This function exists purely to extract those raw year/month numbers — from two different columns (InvoiceMonth and Cohort Month) — without writing the same three lines twice.

Line-by-line explanation

  • def get_date_elements(df, column):
    What: defines a function taking two parameters — df (which table to look in) and column (which column name, as a string, to pull dates from). Why two parameters: this makes the function generic — cell 7 will call it twice, once for 'InvoiceMonth' and once for 'Cohort Month', without rewriting the logic.
  • day = df[column].dt.day
    What: the .dt accessor unlocks date-specific properties on a datetime column; .day extracts just the day-of-month as a plain integer for every row. Common mistake: forgetting .dt and writing df[column].day directly — that throws an AttributeError, because .day only exists on individual timestamp objects, not on an entire Series; .dt is the bridge that applies it element-wise.
  • month = df[column].dt.month
    Same pattern as above, extracting the month number (1–12).
  • year = df[column].dt.year
    Same pattern, extracting the 4-digit year.
  • return day, month, year
    What: returns all three Series together as a tuple of three values in one return statement. Why it matters: Python lets you "unpack" a returned tuple straight into three separate variable names at the call site (exactly what cell 7 does) — a compact, very common Python pattern.

📦 Concept: the .dt accessor

When a pandas column holds dates (dtype datetime64), you can't call date methods on the column directly — you have to go through .dt first, which tells pandas "apply this date logic to every value in the Series, one at a time, and give me back a new Series of results."
Analogy .dt is like a translator standing between you and a room full of calendar pages — you ask the translator "get me everyone's month," and it walks the whole room asking each page individually, then hands you back one big list of answers.

Cell 10

Create the Cohort Index — the whole notebook's core formula

#create a cohort index
year_diff = Invoice_year -Cohort_year
month_diff = Invoice_month - Cohort_month

data.tail()

What this cell does

Computes, for every single transaction, exactly how many months have passed since that customer's very first purchase — and stores it as a new column, CohortIndex, where 1 = "the month they joined," 2 = "one month later," 3 = "two months later," and so on.

Why this cell exists

This is the number that makes the whole retention heatmap possible. Once every row knows both which cohort it belongs to (Cohort Month) and how many months into that cohort's life this purchase happened (CohortIndex), you can finally ask the real business question: "of the people who joined in December, how many were still buying in month 3? Month 6? Month 12?" — and compare that shape across every cohort side by side, regardless of which actual calendar month each cohort started in.

Line-by-line explanation

  • year_diff = Invoice_year - Cohort_year
    What: subtracts two whole Series element-by-element (row 1 of Invoice_year minus row 1 of Cohort_year, row 2 minus row 2, etc. — pandas aligns by position/index automatically). Why: if a purchase happens in a later calendar year than the customer's first purchase, this captures how many full years apart they are. Common mistake: assuming this line alone gives you "months apart" — it only gives years apart; the month component still needs separate handling below.
  • month_diff = Invoice_month - Cohort_month
    What: similarly subtracts the month numbers (1–12) for the same reason. Important subtlety: this can be negative — e.g. a customer acquired in November (month 11) buying again in January (month 1) gives 1 - 11 = -10. That's fine and expected; the next line's year_diff*12 term corrects for it (Jan is year_diff=1, so 1*12 + (-10) = 2, correctly landing on month 2 of that customer's life).
  • data['CohortIndex'] = year_diff*12+month_diff+1
    What: converts the (year, month) difference pair into a single "total months elapsed" number, then adds 1 so a customer's very first purchase month reads as index 1 rather than index 0 (a deliberate, human-friendly choice — "month 1" instead of "month 0" matches how people naturally count). Why *12: converts whole years into their month-equivalent (2 years = 24 months) so it can be added directly to the month difference. Common mistake: forgetting the final +1 and ending up with cohort index 0 for the acquisition month, which is technically fine but inconsistent with how this notebook (and most retention reports) label the first month.
  • data.tail()
    Confirms the new column landed correctly by inspecting the last 5 rows, same habit as cell 4.

📦 Concept: why "year_diff × 12 + month_diff" works

There's no single built-in "months between two dates" operator in plain arithmetic, because a month isn't a fixed number of days. The trick is to convert both dates into "total months since year 0" conceptually: total_months = year × 12 + month. Subtracting two such totals gives you the month gap directly — which is exactly what year_diff*12 + month_diff computes, just split across two separate subtraction steps instead of one.
Analogy Think of every month since year zero as one tick on a single ruler (Jan 2010 = tick #24120, Feb 2010 = tick #24121, and so on). Once two dates are just tick numbers on the same ruler, "how far apart" is plain subtraction — no calendar logic needed anymore.

What this cell does

Divides every value in each row by that same row's first column (its CohortIndex-1 value — the cohort's original size), converting every cell from "how many customers" into "what fraction of the original cohort" — i.e. the actual retention rate.

Why this cell exists

This directly fixes the limitation flagged at the end of cell 13: comparing raw counts across cohorts of different sizes (948 vs. 41 people) isn't a fair comparison. Dividing every row by its own starting size puts every cohort on the same 0%–100% scale, so you can honestly compare "did the December cohort retain better than the June cohort?" regardless of how many people were originally in each.

Line-by-line explanation

  • cohort_table.iloc[:,0]
    What: selects every row, but only the first column (position 0) — which, since CohortIndex starts at 1, is always the "month 1" column: each cohort's full original size. Why .iloc: selects by integer position rather than by label, which matters here because the actual column label is the number 1, and .iloc[:,0] unambiguously means "first column, whatever its label is."
  • cohort_table.divide(cohort_table.iloc[:,0], axis=0)
    What: divides the entire table by that one-column Series, row-by-row. Why axis=0: this is the critical parameter — it tells pandas "match up and divide along the row axis," i.e. every value in row X gets divided by row X's own starting size, not by some single global number. Without axis=0, pandas would try to align by column instead, which wouldn't broadcast correctly against a single-column Series and would produce wrong or NaN-filled results. What's returned: a new DataFrame the same shape as cohort_table, but every value now between 0 and 1 (0% to 100%), with the first column always exactly 1.0 (100% — every cohort retains 100% of itself, by definition, in its own first month).

📦 Concept: retention rate (and its cousin, churn)

Retention rate is the percentage of an original group that is still active at a later point in time — here, still making purchases N months after joining. Its mirror opposite is churn rate (the percentage who left). Retention is one of the most-watched metrics at any subscription, app, or e-commerce business, because it's usually far cheaper to keep an existing customer than acquire a brand-new one.
Analogy Imagine 100 people join a gym in January. If 38 of them still show up in March, that's a 38% retention rate at month 3 — completely independent of whether the gym signed up 100 or 10,000 people that January. That normalization (dividing by the original group size) is exactly what this cell's .divide(...) call does.
Interview angle: be ready to explain that retention curves almost always drop steeply at first, then flatten — the "survivors" left after the initial cliff tend to be genuinely loyal customers, which is a hugely useful insight for a business.

Common interview questions (cross-notebook)

💬 8 rapid-fire questions spanning the whole notebook

1. What is cohort analysis, in one sentence?
Grouping users by a shared starting event (like acquisition month) and tracking their behavior over time relative to that starting point, so different groups can be compared fairly.

2. Why round dates down to the month instead of analyzing exact days?
To create a shared, groupable time bucket — daily granularity would make almost every timestamp unique and impossible to meaningfully group.

3. Explain the difference between transform() and agg() with an example.
agg() collapses a group to one summary row; transform() broadcasts that summary back onto every row in the group, preserving the original shape — needed here to attach group-level facts (like Cohort Month) back onto the full transaction table.

4. Why use nunique() instead of count() when measuring "active customers"?
count() would count every transaction row, double-counting customers who bought multiple items; nunique() counts distinct people.

5. Why convert the raw-count heatmap into percentages?
To fairly compare retention across cohorts of very different original sizes on the same 0-100% scale.

6. What would you check first if the pivot() call raised a duplicate-entry error?
Whether the upstream groupby actually collapsed to unique (index, column) combinations — likely a missed aggregation step.

7. What business decisions could this retention heatmap directly inform?
Where to focus onboarding/retention spend (usually right after the first purchase, where the steepest drop tends to occur), and whether changes over time (marketing, pricing, product) are improving or worsening retention.

8. What's one limitation of this specific analysis worth mentioning in an interview?
~25% of transactions were dropped for missing CustomerID, which could bias the results if those missing IDs aren't random (e.g. if they're disproportionately guest checkouts or cancellations).
